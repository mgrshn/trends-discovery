# Руководство по сервису Trends Discovery

## Что это такое

Сервис собирает темы из Google Trends, оценивает их рост и отображает в виде дашборда. Основная задача — находить темы, которые начинают набирать популярность раньше, чем они станут мейнстримом.

Сервис состоит из двух частей:
- **Frontend** — React-приложение, которое видит пользователь
- **Backend** — Laravel-приложение, которое управляет данными и фоновыми задачами

Данные из Google Trends получает отдельный сервис-парсер (`google-trends-parser`). Discovery общается с ним только по HTTP — никакого прямого доступа к его базе данных.

---

## Что видит пользователь

### Вкладка Real-time

Показывает темы, которые прямо сейчас в тренде в Google — «горячие тренды» за последние 24 часа.

**Как работает:** при открытии вкладки фронтенд делает запрос к нашему API, которое в реальном времени обращается к парсеру → парсер спрашивает Google → возвращает список тем с объёмом поиска и ростом. Данные не кешируются на нашей стороне, каждый раз свежие с Google.

Пользователь выбирает страну в дропдауне — список тем меняется. Worldwide в этом режиме недоступен (Google Trends не поддерживает глобальный Trending Now).

### Вкладка Long-term

Показывает темы из **нашей базы данных** — те, что мы накопили за время работы и уже оценили скорингом.

**Как работает:** никакого обращения к парсеру при открытии не происходит. Всё берётся из PostgreSQL. Темы фильтруются по статусу, категории, стране. Доступен Worldwide (агрегат по всем странам).

Статусы тем:
- **Exploding** — резкий рост, тема взрывает прямо сейчас
- **Regular** — стабильный умеренный рост
- **Peaked** — рост закончился, тема прошла пик
- **Noise** — недостаточно данных для выводов

### Trend Analysis

Поиск любого ключевого слова и получение подробной аналитики по нему:
- График интереса за выбранный период (3 месяца / 6 / 12 / 5 лет)
- Похожие запросы (Rising — резко растущие, Top — исторически популярные)
- Интерес по регионам

**Как работает:** при нажатии Analyze идёт запрос к нашему API, который параллельно спрашивает парсер по трём эндпоинтам: `/trends` (временной ряд), `/trends/related` (связанные запросы), `/trends/regions` (регионы). Сначала ждёт `/trends` (он может занять время при первом запросе), потом два остальных одновременно.

Парсер кеширует данные у себя — повторный запрос по тому же ключевому слову отдаётся значительно быстрее.

## Как данные попадают в базу

### Шаг 1 — Ingest (сбор горячих трендов)

Каждые N минут (по умолчанию 30, настраивается) для каждой выбранной страны запускается `IngestTrendingJob`. Он:
1. Спрашивает парсер: «дай мне топ-100 горячих тем в стране X за последние 24 часа, отсортированных по росту»
2. Получает список тем с объёмом, процентом роста, категорией Google и breakdown-запросами
3. Записывает каждую тему в таблицу `topics` (upsert по паре keyword+geo — если тема уже есть, обновляет объём и рост)
4. Записывает breakdown-темы отдельными строками с пометкой `source=breakdown`
5. Автоматически запускает два следующих шага для этой страны

После каждого ingest сразу запускаются:
- `SparklineFetchJob` — за спарклайном (мини-графиком) для топ-20 новых тем по этой стране
- `ScoreTopicsJob` — скоринг для 20 ещё не оценённых тем

### Шаг 2 — Спарклайн

`SparklineFetchJob` берёт до 20 тем для страны, у которых ещё нет спарклайна, и для каждой запрашивает у парсера тренд за 3 месяца. Результат — массив из ~13 чисел (0–100) — сохраняется как JSON в поле `sparkline`. Именно этот мини-график показывается в карточках на дашборде.

### Шаг 3 — Скоринг

`ScoreTopicsJob` берёт до 100 тем, которые ещё не оценены (или оценивались больше 7 дней назад), и для каждой:
1. Запрашивает у парсера тренд за **12 месяцев** — именно здесь мы ходим в Google для подсчёта скора
2. Рассчитывает метрики своими силами (см. ниже)
3. Обновляет статус, скор и цифры роста в базе
4. Записывает снепшот в `topic_metrics_history`

Все 100 запросов к парсеру идут **параллельно**. Если парсер отвечает 202 (данные собираются), повторяет через 2 секунды, до 5 попыток.

### Шаг 4 — Related Rising

Раз в 6 часов `RelatedRisingIngestJob` берёт топ-30 тем со статусом Exploding или Regular, отсортированных по скору, и для каждой запрашивает у парсера «похожие rising-запросы» за 12 месяцев. Новые темы добавляются в базу с источником `source=related_rising`. Уже существующие темы получают обновление growth_pct.

## Как считается скор

Скор считается полностью на нашей стороне — PHP-код, никакого ML. Входные данные — недельный временной ряд интереса из Google (значения 0–100) за 12 месяцев (~52 точки).

**Шаги:**
1. Сглаживание скользящим средним по 4 неделям — убирает шум
2. Вычисление нескольких метрик:
   - **Slope** — наклон лог-линейной регрессии за последние 12 недель (крутизна роста)
   - **Acceleration** — разница наклонов за последние 6 недель vs предыдущие 6 (ускорение)
   - **SMA Ratio** — отношение среднего за 4 недели к среднему за 12 недель (краткосрочный импульс vs долгосрочный)
   - **Volatility** — коэффициент вариации (штрафуем хаотичные темы)
   - **Seasonality** — корреляция Пирсона с лагом 52 недели (штрафуем сезонные темы)
   - **Volume** — логарифм объёма поиска (небольшой бонус популярным темам)

**Итоговый скор** — взвешенная сумма:
```
score = 40 × slope
      + 10 × acceleration
      + 20 × (smaRatio - 1)
      + 10 × log(volume + 1) / 15
      -  5 × seasonality
      -  5 × volatility
```

**Статус определяется отдельно от скора:**

| Статус | Условия |
|--------|---------|
| **Peaked** | Slope за последние 12 недель < −0.015 ИЛИ slope за весь период < −0.015 |
| **Exploding** | Slope > 0.025 И SMA Ratio > 1.05 И не разовый событийный spike И общий тренд не падает И средний уровень за последние 4 недели ≥ 15 |
| **Regular** | Всё остальное |
| **Noise** | Меньше 8 точек данных ИЛИ меньше 20% точек > 2 (тема слишком малоизвестна) |

**Событийный spike** — если был один резкий пик (z-score > 2.5), пик произошёл в последней трети периода, и текущий уровень упал ниже 50% от пика. Такие темы не получают Exploding даже с высоким slope.

## Когда и как часто мы ходим в парсер

Все автоматические обращения **работают только при включённом Auto-parse** в настройках. Ручные запросы (Real-time вкладка, Trend Analysis) работают всегда.

| Когда | Что | Эндпоинт парсера | Кол-во запросов |
|-------|-----|------------------|-----------------|
| Каждые N минут (авто) | Ingest горячих трендов | `GET /trending` | 1 на страну × кол-во выбранных стран |
| После каждого ingest | Спарклайны | `GET /trends` (3m) | до 20 на страну |
| После каждого ingest | Предварительный скоринг | `GET /trends` (12m) | до 20, параллельно |
| Каждый час (авто) | Полный батч скоринга | `GET /trends` (12m) | до 100, параллельно |
| Каждые 6 часов (авто) | Related Rising | `GET /trends/related` | до 30 |
| По нажатию пользователя | Real-time вкладка | `GET /trending` | 1 |
| По нажатию пользователя | Trend Analysis | `GET /trends` + `GET /trends/related` + `GET /trends/regions` | 3 параллельно |
| /api/health | Healthcheck | `GET /health` | 1 |

При **выключенном Auto-parse** автоматические задачи не запускаются. Парсер не дёргается вообще — кроме ручных действий пользователя во фронтенде и кнопок «Parse now» / «Recalculate scores» в админке.

## Админ-панель (`/admin`)

### Parser Settings

Основная страница управления парсингом.

**Настройки:**
- **Enable auto-parsing** — главный рубильник. При выключении останавливаются все три автоматических процесса: ingest, скоринг и related rising. Ручные действия пользователя на фронтенде продолжают работать.
- **Parse interval** — как часто запускать ingest (5 / 10 / 15 / 30 / 45 / 60 минут)
- **Geos to parse** — список стран для парсинга. По умолчанию 51 страна. Можно выбрать только нужные — например, только англоязычные рынки. Чем меньше стран, тем быстрее проходит каждый ingest и меньше нагрузка на парсер.

**Кнопки:**
- **Parse now** — разовый немедленный запуск ingest. Открывает модальное окно с выбором стран. Если ничего не выбрать — запускается по всем выбранным в настройках.
- **Recalculate scores** — немедленно запустить скоринг для 100 ещё не оценённых тем. Полезно при первичном наполнении базы.
- **Save settings** — сохранить настройки.

### Jobs Monitor

Мониторинг состояния системы в реальном времени.

**Статус парсера** — зелёный/красный индикатор доступности парсера. Проверяется при каждом открытии страницы запросом к `GET /health` парсера.

**Счётчики:**
- **Pending jobs** — сколько задач сейчас в очереди Redis ждут обработки
- **Failed jobs** — сколько задач упало и не смогло завершиться (после всех попыток ретрая)
- **Scored today** — сколько тем получили скоринг сегодня
- **Topics total** — общее количество тем в базе
- **Topics scored** — сколько тем хоть раз были оценены

**Таблицы:**
- **Pending jobs** — первые 20 задач в очереди (что и в каком порядке будет обработано)
- **Failed jobs** — упавшие задачи с текстом ошибки. Можно ретрайнуть отдельную или сразу все. Можно удалить.

**Кнопки в шапке:**
- **Retry all failed** — поставить все упавшие задачи в очередь снова
- **Clear all failed** — удалить все упавшие задачи без повторного запуска

Ссылка **Open Horizon dashboard** ведёт на `/horizon` — детальный мониторинг очередей.

### Proxies

Управление прокси-серверами для парсера. Прокси хранятся в самом парсере и используются им при обращениях к Google Trends — чтобы не получить бан по IP.

Страница загружает список прокси из парсера через API и позволяет:
- Добавить прокси (формат: `http://user:pass@host:port` или `socks5://host:port`)
- Включить / отключить отдельный прокси
- Проверить прокси — парсер пробует через него выйти в интернет и возвращает результат (OK/Failed, задержку, IP выхода)
- Удалить прокси

**Важно:** изменения применяются к парсеру-воркеру только после его перезагрузки:
```bash
docker compose kill -s HUP parser-worker-1
```
Об этом показывается предупреждение после каждого изменения.

### Topics

Таблица всех тем в базе. Поиск, фильтрация по статусу / категории / источнику / стране. Можно редактировать любое поле вручную — например, вручную задать статус или категорию.

## Horizon (`/horizon`)

Laravel Horizon — это дашборд очередей. Показывает детальную статистику по обработке задач.

**Что смотреть:**
- **Dashboard** — общий throughput: сколько задач обработано в секунду/минуту
- **Queues** — состояние каждой очереди: размер, ожидающие задачи
- **Recent Jobs** — последние выполненные задачи с временем обработки
- **Failed Jobs** — та же таблица что в Jobs Monitor, но с более детальным стектрейсом
- **Monitoring** — можно добавить метрики для слежения

Horizon использует Redis для хранения метрик (хранит историю за последние часы).

---

## Healthcheck

`GET /api/health` — проверяет состояние сервиса.

Пример ответа при норме:
```json
{
  "status": "ok",
  "service": "trends-discovery",
  "parser": {
    "url": "http://parser:8000",
    "reachable": true
  }
}
```

При недоступности парсера возвращает HTTP 503 и `"status": "degraded"`.

Используется для мониторинга (uptime-сервисы, балансировщики нагрузки).

## Что происходит при первом запуске

1. Контейнер backend стартует и автоматически:
   - Применяет миграции базы данных
   - Публикует статические файлы Filament
   - Засевает таблицу категорий (20 категорий с маппингом Google-ID)
   - Кеширует конфиг и роуты

2. Если Auto-parse включён — через N минут (или сразу после ручного Parse now) запускается первый ingest по всем выбранным странам. 51 страна × до 100 тем = до 5100 тем за первый проход.

3. Параллельно с ingest-ом автоматически запускается предварительный скоринг (20 тем) и спарклайны (20 тем) для каждой страны.

4. Каждый час добавляется ещё 100 оценённых тем. При 14 000 тем и отсутствии ранее накопленной базы — полный скоринг займёт несколько дней при стандартных настройках.

## Автовосстановление при сбоях

| Что упало | Кто поднимает | Когда |
|-----------|---------------|-------|
| Отдельная задача в очереди | Horizon (автоматический ретрай) | IngestTrendingJob — 3 попытки, ScoreTopicsJob — 2 попытки, SparklineFetchJob — 2 попытки |
| Horizon-процесс (воркер) | Docker (`restart: unless-stopped`) | Немедленно |
| Scheduler | Docker (`restart: unless-stopped`) | Немедленно |
| Backend | Docker (`restart: unless-stopped`) | Немедленно |
| Парсер недоступен временно | Задача уйдёт в failed после исчерпания ретраев; следующий ingest запустится по расписанию | По расписанию (через N минут) |
