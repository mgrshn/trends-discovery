## Открытые вопросы (требуют ответа от владельца)

- **2026-07-07 [ОТКРЫТ]** · **Качество данных дашборда** — источник данных дашборда сейчас `/trending` парсера, что даёт события текущего дня (новости). Это создаёт шум: топики типа «Boeing 737 MAX Emergency» появляются в категории Entertainment из-за ненадёжного автоматического маппинга Google. **Вопрос:** дашборд должен показывать _долгосрочные_ тренды (то, что растёт неделями) или _реальное время_ (что ищут сегодня)? Если долгосрочные — источником должен быть не `/trending`, а наш scored-пайплайн (этап 3), а дашборд до этапа 3 останется пустым или покажет данные без скоринга.

- **2026-07-07 [ОТКРЫТ]** · **Фильтры в Trend Analysis** — в плане Этапа 1 не было параметра `engine` (web/youtube/images/news). Нужно ли добавить выбор движка в UI, или достаточно только keyword + geo + period?

- **2026-07-07** · Этап 2 — спарклайны кешируются в `topics.sparkline` (JSONB, значения 0–100) и наполняются
  фоновым `SparklineFetchJob`, диспатчится после инжеста; на рендер карточки к парсеру не ходим ·
  Дашборд должен отвечать из своей БД мгновенно; спарклайн — производное от `/trends?period=3m`.
- **2026-07-07** · Медленные запросы в Trend Analysis — первый запрос занимает 15–60 с (парсер скрейпит Google); второй мгновенный (кеш парсера). Три вызова делаются последовательно с 202-поллингом. Краткосрочно: оставить поллинг, добавить progress-индикатор в UI. `Http::pool()` отложен — параллельность не помогает, пока 202 упирается в один scrape job. Долгосрочно: WebSocket-пуш «анализ готов» через Reverb (пост-MVP).
- **2026-07-07** · Инжест trending-данных — `IngestTrendingJob` (per-geo, по 7 гео каждые 30 мин),
  Scheduler через `routes/console.php`; breakdown-вариации пишутся с `source='breakdown'`, `seed_keyword` ·
  Одна джоба на гео — проще повторить при ошибке; breakdown дают seed для related-цикла этапа 4.
- **2026-07-07** · Backend — **Laravel** (не Python/FastAPI, не Symfony) · Владелец 3 года на Laravel,
  читает и ревьюит PHP, а не Python — способность ревьюить ядро продукта важнее синергии с парсером
  (сервисы общаются по HTTP, языки по разные стороны границы независимы). Symfony отпадает: тот же
  довод (владелец его не знает), плюс проектно-специфичных причин за него нет.
- **2026-07-07** · Версия стека — **Laravel 13 + Filament 5** (v5.6.8, latest stable на 2026-07-07) ·
  Filament 5 поддерживает `illuminate ^11.28|^12.0|^13.0` и Livewire ^4.1; PHP ^8.2 — в Docker используем
  PHP 8.2-fpm образ. Filament 4 тоже стабилен и поддерживает те же версии, но 5 — текущий latest.
- **2026-07-07** · Frontend — **отдельная React SPA** (Vite+TS+Tailwind+ApexCharts), НЕ Filament-как-продукт
  и НЕ Vue · Отдельный фронт выбран за чистый API-контракт (переносимость, «auth потом» дешевле) и знакомую
  владельцу архитектуру (React+Laravel-API с прошлой работы). React > Vue: владелец оба ревьюит слабо
  (Vue щупал «чутка»), значит перевешивают экосистема дашбордов (Tremor) и объём данных для агентов.
  Filament-как-продукт рассматривали — отклонили: потолок визуала/интерактива для consumer-facing копии.
- **2026-07-07** · Filament — только внутренняя админка/курация, подключить рано · Генерирует админ-CRUD
  бесплатно (замена Nova); продуктовые страницы — в React SPA.
- **2026-07-07** · Скоринг — на PHP (эвристический тир), с опцией вынести тяжёлую статистику
  (STL/сезонность/ML) в Python-сервис за HTTP · Базовая математика тривиальна и её важно ревьюить;
  numpy/statsmodels нужны только для тяжёлого тира, который и так просится в отдельный сервис.
- **2026-07-07** · Вебсокеты — не в MVP; позже Laravel Reverb + Echo, первый кейс — пуш «анализ готов»
  вместо 202-поллинга · Поллинг проще и достаточен для старта; WS добавляют реальную ценность на алертах/ленте.

- **2026-07-07 (унаследовано)** · Монорепо: backend + frontend в одном репозитории discovery ·
  Каждая страница копии = эндпоинт + экран; один PR на фичу, синхронный запуск. Фронт выносится
  за час (`git subtree split`), если понадобится.
- **2026-07-07 (унаследовано)** · Общение с парсером только по HTTP, никакого доступа к его БД ·
  Иначе сервисы срастутся обратно в монолит; парсер остаётся отдельно продаваемым продуктом.
- **2026-07-07 (унаследовано)** · Без авторизации, но `user_id BIGINT NULL` в продуктовых таблицах
  и общий APIRouter с первого дня · «Прикрутить auth потом» = дни вместо переписывания таблиц.
- **2026-07-07 (унаследовано)** · Discovery хранит только производные данные (topics, метрики, статусы)
  и продуктовые сущности; сырые ряды не копирует · Ряды живут в кеше парсера с TTL, при пересчёте
  перезапрашиваются. Нет дублирования и рассинхрона.
- **2026-07-07 (унаследовано)** · Запрос пользователя никогда не запускает скрейпинг (кроме страницы
  Trend Analysis — там это фича) · Каталог/дашборд отвечают из своей БД мгновенно; наполнение фоном.
- **2026-07-07 (унаследовано)** · Скоринг — свой код (~300 строк поверх numpy/statsmodels), ничего
  не форкать · Формулы (наклон, ускорение, z-score, ACF) тривиальны; 0-звёздные репы — AI-генерация.
- **2026-07-07 (унаследовано)** · PostgreSQL, не ClickHouse · Нагрузка = upsert-кеш + точечные чтения,
  это анти-профиль CH. Пересмотреть при аналитических сканах по всей истории (сотни ГБ).
